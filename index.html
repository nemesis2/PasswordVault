    ℹ︎  About Password Vault

    ℹ︎ Description

    Self-hosted, client-side encrypted password manager served by a PHP-capable web server — or, with no PHP at all, by the bundled standalone Node.js server (server.js). All encryption and decryption happens entirely in your browser using the WebCrypto API — the server only stores and serves ciphertext and never sees your plaintext passwords.

    Open source, released under the MIT License.

    Version 1.1.3

    🛠︎ Vault Tools

    Audit decrypts every entry locally and flags reused, weak, fair, empty, or stale (not changed in over a year) passwords — names only are shown and nothing leaves this device; secure notes have no password and are skipped. Passkeys lists which entries store a WebAuthn passkey, by name and site — this app can only view and delete a stored passkey; the companion browser extension is what creates and signs one. Trash lists entries you have deleted so you can restore them or remove them permanently; deletions are kept server-side for up to 30 days (capped at the 100 most recent; ciphertext only). Change Passwords re-encrypts the whole vault under new master passwords in one atomic save. Sign stores a keyed signature (HMAC under your master passwords) over the whole vault; it is checked automatically on every unlock and refreshed after every save, so tampering, corruption, or a rolled-back copy is detected. Use the button only to accept a deliberate manual edit or backup restore as the new baseline.

    🔑︎ Change Master Passwords

    Current passwords are taken from the two key fields above. Every entry is decrypted and re-encrypted in your browser, then saved in a single atomic replace — if anything fails, the vault is left untouched.

    📦︎ Backup & Migration

    Export downloads the encrypted database exactly as stored on the server (ciphertext only). Import restores an exported .lines file, replacing the whole vault in one atomic save — every imported entry is decrypted with the passwords in the key fields first, so an import that does not match those passwords is refused and nothing is changed (the server also keeps a backup of the current vault before importing). Export CSV writes every entry to a plaintext file (passwords, TOTP secrets, and notes in the clear, with none of the vault’s protection) for migrating into another password manager — it warns and asks for confirmation first, and you should delete the file as soon as you are done. Import CSV reads a CSV exported by another manager (Bitwarden, Chrome, 1Password, …) and adds those entries to your vault, re-encrypting each one with the passwords in the key fields (your existing entries are kept). Import KeePass reads a KeePass 2 XML export (File → Export → KeePass XML in KeePass/KeePassXC) and adds those entries the same way. Import 1Password reads a 1Password .1pux export and does the same — the encrypted .kdbx file itself isn’t supported, so export to XML/CSV first.

    ⚙︎ Change KDF Parameters

    Tunes the Argon2id key-derivation cost for the whole vault. Higher values make every unlock slower for you but brute-forcing far slower for an attacker. The change re-encrypts every entry in your browser under the same passwords (taken from the key fields above), then saves in a single atomic replace — if anything fails, the vault is left untouched. Memory must be 64–1024 MiB, iterations 2–10; parallelism is fixed at 1.

    ⧉︎ Viewing & Copying

    Click any entry to fill the display panel at the top with its decrypted fields. The Username, 2FA token, and Password rows are click-to-copy — click anywhere on the row to copy that field to the clipboard. A brief flash confirms the copy.

    Each copyable row carries a dimmed ⧉︎ copy glyph on its right edge that brightens when you hover the row, marking it as copyable at a glance. The glyph is only a visual cue — the whole row is the click target, so copying works the same on touch screens where there is no hover.

    A copied secret is auto-cleared from the clipboard after 45 seconds, and immediately on any lock, so it never lingers there.

    Custom fields appear as their own click-to-copy rows; any marked secret show masked (••••) but still copy on click. If the entry has password history, a collapsible ⏱︎ Password history row lists previously used passwords (each with the date it was replaced), also click-to-copy.

    Next to the password, a 📝︎ Modified column shows the date the password was last changed — or the creation date, if it never has. Hover it for a tooltip with the entry's creation date and age. Entries saved before this tracking existed show a best-effort creation date (prefixed “≤”) inferred from the oldest password-history entry, or the modified date if there is no history — both are upper bounds on the true creation time.

    🏷︎ Organizing & Searching

    Tags. Each entry can carry a comma-separated list of tags (e.g. work, email, personal). Tags are normalized on save — lowercased, trimmed, and de-duplicated — and are stored inside the encrypted payload, exactly like the password and notes, so they are as protected as any other field and never appear in the database in the clear.

    Scoped search. The search overlay matches by a leading character: type plainly to search entry names, prefix with # to search tags (e.g. #work), @ to search notes (e.g. @recovery), or ! to search custom fields — both labels and values (e.g. !PIN). The count line shows which scope is active. Tag, note, and custom-field search read the decrypted payloads cached in memory, so they cover every entry once both passwords are entered and all names have been revealed.

    Group A–Z. The entry grid is always sorted alphabetically; the Group A–Z toggle (beside the entry count, once the vault is unlocked) adds sticky first-letter headers above each run of entries — names not starting with a letter are bucketed under #. The preference is remembered per vault in your browser (on by default).

    Favorites. Click the ☆ star in the display panel (or press F) to favorite the open entry. Favorites pin to the top of the grid — under a ★ Favorites header when grouping is on — and show a ★ on their button. The set is remembered per vault in your browser as a one-way hash of each name (never the name itself), so it survives edits and reveals nothing if local storage is read.

    Custom fields. Entries can carry any number of extra labelled values (added with ➕︎ Add field in the form), each optionally marked secret to mask it in the panel. Like tags, they live inside the encrypted payload and are as protected as every other field.

    Secure notes. The Type toggle at the top of the entry form switches between a Login (URL, username, password, 2FA) and a Secure Note — just a name plus notes, tags, and custom fields, with the credential rows and password generator hidden. The type travels inside the encrypted payload like tags, so it adds no new record format; note entries show a 📝︎ badge on their button and are skipped by Audit (there is no password to check).

    Multi-select. The ☑︎ Select control beside Group A–Z turns the grid into a checklist — click entries to toggle their selection, then use the bar that appears at the bottom to Favorite, Tag…, or Delete all of them in one save. Bulk delete can’t empty the vault (leave at least one entry off, or delete the last one individually) and offers an Undo for a few seconds afterward; bulk tag merges the typed tags into each selected entry without touching its other fields.

    ✍︎ Vault Signing

    Every save automatically signs the entire record set with a keyed HMAC that only a password holder can produce. The server stores the signature opaquely — it has no access to your passwords and can never forge or verify it. On every unlock, the browser recomputes the signature over the records it received and compares. Any discrepancy — an entry tampered with, silently deleted, or corrupted — is shown as a red failure badge rather than passing unnoticed.

    Signature construction

    Vault keyHKDF-SHA-256 over Argon2id(pw1, salt1) ‖ Argon2id(pw2, salt2), info v6|manifest|hmac — independent of every per-record key
    Signed dataHeader fields (format, salts, revision, timestamp) + every record joined in canonical server order
    AlgorithmHMAC-SHA-256 via WebCrypto
    RevisionMonotonic counter incremented on every sign; each device remembers the highest revision it has seen, so a validly signed but older copy of the vault raises a rollback alert

    Manifest format (stored server-side, embedded in the served page):

    vm1 | salt1 | salt2 | revision | timestamp | hmac

    Limits: this is tamper detection for the data file. It guards against corruption, botched restores, and manual-edit mistakes. It cannot defend against an adversary who can also rewrite the served JavaScript — no in-band scheme can.

    🗂︎ Record Formats

    Record format (v6) — doubly-encrypted name:

    encName | v6 | recSalt1 | recSalt2 | nameNonce1 | nameNonce2 | iv1 | nonce2 | nonce3 | nonce4 | ciphertext

    recSalt1 and recSalt2 are the two Argon2id salts (one per master password); every per-cipher key is HKDF-derived from the resulting master keys, so the record carries only nonces, not per-layer salts. The entry name is double-encrypted: AES-256-GCM (password 1) as the inner layer, wrapped by ChaCha20-Poly1305 (password 2) as the outer layer. Both passwords are required to reveal the name. Entry buttons are hidden on page load; they appear automatically when both key fields contain a value and the secondary key field loses focus.

    Records are stored in a flat file, one per line, sorted by the raw bytes of the full encrypted record — since the name itself is encrypted, that is not alphabetical by name; it just keeps the file in a stable, deterministic order. The entry grid you see is re-sorted alphabetically in the browser, by the real name, after it is decrypted. Each button also carries its line index as an informational 12th field, but it is never used to identify a record — delete and edit always reference the full record string instead, so a concurrent change elsewhere can't make an operation land on the wrong line.

    The encrypted payload (ciphertext) is a JSON object holding the URL, username, password, 2FA token, notes, tags, custom fields, password history, creation / password-modified timestamps, an optional entry type (login or secure note), and an optional passkey (WebAuthn credential). These all live inside the same encrypted blob — the record format itself is unchanged, so every one of them is as protected as the password.

    🔑︎ Key Derivation

    Each record derives two 256-bit master keys with memory-hard Argon2id (default m = 128 MiB, t = 3, p = 1, adjustable per vault in Change KDF Parameters) — one per master password, each over a 32-byte random salt generated fresh for every save. HKDF-SHA-256 then expands each master key into the independent per-cipher subkeys (distinct info labels), so the expensive memory-hard step runs only twice per record while every layer still gets its own key.

    The memory-hard step is what makes an offline brute-force attack infeasible: every single password guess costs a full memory pass (128 MiB at the default cost) plus significant CPU time, so a GPU farm that tests billions of fast hashes per second is reduced to a few thousand Argon2id guesses per second per card. Combined with a strong, unique second password, this raises the cost of guessing the vault open to be computationally prohibitive.

    Revealing many entry names at once would otherwise serialise the memory-hard hashes on the main thread (the WASM runs synchronously behind an internal mutex). To keep the UI responsive, each derivation is dispatched to a pool of dedicated Web Workers — one WebAssembly instance each — so peak memory stays bounded at pool × the per-worker heap (128 MiB at the default cost). The pool is sized at the reported CPU core count — capped at 24 on desktop and 2 on phones/tablets (less RAM, thermal throttling) — and further bounded by available device memory so the heaps stay within roughly half of RAM. It is created lazily and torn down on every lock, reclaiming its WASM heaps and dropping residual password bytes. A derivation that fails transiently (memory pressure, a worker crash) is retried — falling back to the main thread between attempts — so an entry is never silently dropped from the grid; if Workers are unavailable entirely, derivation runs on the main thread.

    ⛓︎ Encryption Pipeline

    Plaintext JSON → Pad to 256 B → ChaCha20-Poly1305 → AES-256-GCM → Twofish-256-CTR → Serpent-256-CTR → Stored hex
    Layer 1 ChaCha20-Poly1305 — AEAD — password 1, 12-byte nonce
    Layer 2 AES-256-GCM — AEAD — password 1, 12-byte IV
    Layer 3 Twofish-256-CTR — password 2, 16-byte nonce (unauthenticated; relies on inner AEAD layers for integrity)
    Layer 4 Serpent-256-CTR — password 2, 16-byte nonce (unauthenticated; relies on inner AEAD layers for integrity)

    The two inner AEAD layers authenticate the ciphertext. A wrong password or tampered data causes immediate authentication failure before any plaintext is revealed.

    Both passwords are required. Layers 1–2 use password 1 and layers 3–4 use password 2 (the entry name is split the same way — AES-256-GCM under password 1, ChaCha20-Poly1305 under password 2), so an attacker who compromises one password alone learns nothing about names or payload.

    Length-hiding padding. Before the first layer, the plaintext JSON is padded up to the next 256-byte boundary with trailing spaces. The stored ciphertext length therefore reveals only which 256-byte bucket an entry falls into — not the true length of a password or note — so someone who obtains the raw database cannot tell a short password from a long one. The padding is valid trailing JSON whitespace, so it is discarded automatically on decrypt with no separate un-pad step.

    🛡︎ Cipher Rationale

    The four layers span three independent cipher families from different design lineages. An attacker breaking the stored ciphertext must defeat all four simultaneously — breaking AES does not weaken ChaCha20, Twofish, or Serpent. Each cipher was chosen to complement the others' failure modes.

    ChaCha20-Poly1305 AEAD Stream cipher designed by Daniel J. Bernstein. No S-box lookups — constant-time by construction, immune to cache-timing attacks. Adopted in TLS 1.3, SSH, and WireGuard as the standard software-path cipher. The Poly1305 tag authenticates the ciphertext; a wrong password or tampered byte causes immediate rejection before any plaintext is produced.
    AES-256-GCM AEAD The global standard block cipher, NIST-standardised and FIPS 140-2 compliant. Hardware-accelerated (AES-NI) on all modern CPUs. The most widely analysed cipher in existence. GCM adds a Galois-field authentication tag, giving full authenticated encryption. Used here as the second AEAD layer so two independent authentication checks must both pass.
    Twofish-256-CTR CTR AES finalist (top 5), designed by Bruce Schneier, John Kelsey, Doug Whiting, David Wagner, Chris Hall, and Niels Ferguson. Key-dependent S-boxes and a Feistel structure entirely different from AES’s SubBytes/ShiftRows/MixColumns design. Adds a third independent key under password 2, so an attacker who knows password 1 still cannot read the plaintext.
    Serpent-256-CTR CTR AES finalist that came second in the panel vote, designed by Ross Anderson, Eli Biham, and Lars Knudsen. Chosen by the designers specifically for its conservative security margin: 32 rounds (vs AES’s 14), with a simple bitslice structure that has resisted cryptanalysis for over 25 years. The outermost layer — any weakness in layers 1–3 is still protected here.

    Argon2id (PHC winner, 2015) sits in front of all four ciphers as the memory-hard key-derivation step — see Key Derivation above for the cost parameters and why they make offline brute-force infeasible.

    The overall result: even if an attacker obtains the raw ciphertext file, they face four independent cipher layers with independent HKDF-derived keys, two independent AEAD authentication checks, and a memory-hard KDF that serialises every guess — all of which must be overcome before a single password is revealed.

    ⏱︎ TOTP (2FA)

    The token field accepts a bare Base32 secret — the common case, defaulting to a 6-digit code on a 30-second window via HMAC-SHA-1 (RFC 6238) — or a full otpauth:// URI, which can override the digit count, period, and hash algorithm (SHA-1 / SHA-256 / SHA-512), including Steam Guard's 5-character codes. Either way the token is encrypted with the rest of the entry, and the live code's countdown ring follows whichever period the entry actually uses.

    The 📷 Scan QR button in the new-entry form uses the browser's BarcodeDetector API to read a TOTP QR code from a photo or image file. A plain default TOTP stores just the secret; a URI with non-default digits/period/algorithm or Steam Guard keeps the full otpauth:// URI so those settings survive. The issuer and account name pre-fill the Name and Username fields if they are empty. Requires Chrome 83+, Edge 83+, or Safari 17.4+.

    📊︎ Password Strength

    While typing a password in the new-entry form, a six-segment bar and label estimate strength from the character classes present (lowercase, uppercase, digits, symbols) and the password length. Entropy is reported in bits.

    Weak< 40 bits
    Fair40 – 79 bits
    Strong80 – 119 bits
    Very Strong120 – 159 bits
    Exceptional160 – 199 bits
    Paranoid≥ 200 bits

    The two master password fields share a second bar that scores their combined strength (using higher thresholds, since two independent passwords should together be harder to guess than one entry password). If the combined score falls under the lowest tier, the ＋ New button is disabled and reads Too Weak until a stronger pair is entered. The same combined scoring drives the strength bar in Change Passwords.

    🗄︎ Key Caching

    Argon2id master keys are memoised per (password, salt) pair for the duration of the session, so each entry incurs only its two memory-hard derivations once. Clicking an entry after reveal-all reuses the cached master keys (no further Argon2id work). The cache is wiped on auto-lock or manual clear.

    ⌛︎ Auto-lock

    After 5 minutes of inactivity a 60-second warning appears. If not dismissed, all key fields and cached keys are cleared from memory.

    This preference is remembered on this device and stays in effect across reloads and vault locks until you turn it back on.
