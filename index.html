    ℹ︎  Password Vault

    Description

    Self-hosted, client-side encrypted password manager served by a PHP-capable web server. All encryption and decryption happens entirely in your browser using the WebCrypto API — the server only stores and serves ciphertext and never sees your plaintext passwords.

    Open source, released under the MIT License.

    Vault Tools

    Export downloads the encrypted database exactly as stored on the server (ciphertext only). Audit decrypts every entry locally and flags reused, weak, or empty passwords — names only are shown and nothing leaves this device. Change Passwords re-encrypts the whole vault under new master passwords in one atomic save.

    Current passwords are taken from the two key fields above. Every entry is decrypted and re-encrypted in your browser, then saved in a single atomic replace — if anything fails, the vault is left untouched.

    Record Formats

    Record format (v6) — doubly-encrypted name:

    encName | v6 | recSalt1 | recSalt2 | nameNonce1 | nameNonce2 | iv1 | nonce2 | nonce3 | nonce4 | ciphertext

    recSalt1 and recSalt2 are the two Argon2id salts (one per master password); every per-cipher key is HKDF-derived from the resulting master keys, so the record carries only nonces, not per-layer salts. The entry name is double-encrypted: AES-256-GCM (password 1) as the inner layer, wrapped by ChaCha20-Poly1305 (password 2) as the outer layer. Both passwords are required to reveal the name. Entry buttons are hidden on page load; they appear automatically when both key fields contain a value and the secondary key field loses focus.

    Records are stored in a flat file, one per line, sorted alphabetically. The line index is appended at runtime for delete operations.

    Key Derivation

    Each record derives two 256-bit master keys with memory-hard Argon2id (m = 64 MiB, t = 3, p = 1) — one per master password, each over a 32-byte random salt generated fresh for every save. HKDF-SHA-256 then expands each master key into the independent per-cipher subkeys (distinct info labels), so the expensive memory-hard step runs only twice per record while every layer still gets its own key.

    Revealing many entry names at once would otherwise serialise the memory-hard hashes on the main thread (the WASM runs synchronously behind an internal mutex). To keep the UI responsive, each derivation is dispatched to a pool of dedicated Web Workers — one WebAssembly instance each, up to 4 in parallel — so peak memory stays bounded at pool × 64 MiB. The pool is created lazily and torn down on every lock, reclaiming its WASM heaps and dropping residual password bytes. If Workers are unavailable, derivation falls back to the main thread.

    Encryption Pipeline

    Plaintext JSON → ChaCha20-Poly1305 → AES-256-GCM → Twofish-256-CTR → Serpent-256-CTR → Stored hex
    Layer 1 ChaCha20-Poly1305 — AEAD — password 1, 12-byte nonce
    Layer 2 AES-256-GCM — AEAD — password 1, 12-byte IV
    Layer 3 Twofish-256-CTR — password 2, 16-byte nonce (unauthenticated; relies on inner AEAD layers for integrity)
    Layer 4 Serpent-256-CTR — password 2, 16-byte nonce (unauthenticated; relies on inner AEAD layers for integrity)

    The two inner AEAD layers authenticate the ciphertext. A wrong password or tampered data causes immediate authentication failure before any plaintext is revealed.

    Two-Password Design

    Layers 1 and 2 use password 1; layers 3 and 4 use password 2. Both passwords are required to decrypt any entry. Either password alone reveals nothing about the stored data.

    The entry name is protected by both passwords as well: the inner AES-256-GCM layer uses password 1; the outer ChaCha20-Poly1305 layer uses password 2. An attacker who compromises one password cannot reveal entry names or payload.

    Cipher Rationale

    The four layers span three independent cipher families from different design lineages. An attacker breaking the stored ciphertext must defeat all four simultaneously — breaking AES does not weaken ChaCha20, Twofish, or Serpent. Each cipher was chosen to complement the others' failure modes.

    ChaCha20-Poly1305 AEAD Stream cipher designed by Daniel J. Bernstein. No S-box lookups — constant-time by construction, immune to cache-timing attacks. Adopted in TLS 1.3, SSH, and WireGuard as the standard software-path cipher. The Poly1305 tag authenticates the ciphertext; a wrong password or tampered byte causes immediate rejection before any plaintext is produced.
    AES-256-GCM AEAD The global standard block cipher, NIST-standardised and FIPS 140-2 compliant. Hardware-accelerated (AES-NI) on all modern CPUs. The most widely analysed cipher in existence. GCM adds a Galois-field authentication tag, giving full authenticated encryption. Used here as the second AEAD layer so two independent authentication checks must both pass.
    Twofish-256-CTR CTR AES finalist (top 5), designed by Bruce Schneier, John Kelsey, Doug Whiting, David Wagner, Chris Hall, and Niels Ferguson. Key-dependent S-boxes and a Feistel structure entirely different from AES’s SubBytes/ShiftRows/MixColumns design. Adds a third independent key under password 2, so an attacker who knows password 1 still cannot read the plaintext.
    Serpent-256-CTR CTR AES finalist that came second in the panel vote, designed by Ross Anderson, Eli Biham, and Lars Knudsen. Chosen by the designers specifically for its conservative security margin: 32 rounds (vs AES’s 14), with a simple bitslice structure that has resisted cryptanalysis for over 25 years. The outermost layer — any weakness in layers 1–3 is still protected here.

    Argon2id — making brute-force infeasible. Before any cipher sees a key, each password is passed through Argon2id (PHC winner, 2015) with 64 MiB of RAM and 3 passes. This means every single password guess an attacker makes requires 64 MiB of memory and significant CPU time. A GPU farm that can test billions of bcrypt hashes per second is reduced to a few thousand Argon2id guesses per second per card. Combined with a strong, unique second password, this raises the cost of an offline brute-force attack to be computationally prohibitive.

    The overall result: even if an attacker obtains the raw ciphertext file, they face four independent cipher layers with independent HKDF-derived keys, two independent AEAD authentication checks, and a memory-hard KDF that serialises every guess into a 64 MiB, multi-pass operation — all of which must be overcome before a single password is revealed.

    TOTP (2FA)

    HMAC-SHA-1 — RFC 6238 — 30-second window — 6-digit codes.

    Secrets are stored as Base32 in the token field, encrypted with the rest of the entry fields.

    The 📷 Scan QR button in the new-entry form uses the browser's BarcodeDetector API to read a TOTP QR code from a photo or image file. The secret= parameter is extracted from the otpauth:// URI; the issuer and account name are used to pre-fill the Name and Username fields if they are empty. Requires Chrome 83+, Edge 83+, or Safari 17.4+.

    Password Strength

    While typing a password in the new-entry form, a four-segment bar and label estimate strength from the character classes present (lowercase, uppercase, digits, symbols) and the password length. Entropy is reported in bits.

    Key Caching

    Argon2id master keys are memoised per (password, salt) pair for the duration of the session, so each entry incurs only its two memory-hard derivations once. Clicking an entry after reveal-all reuses the cached master keys (no further Argon2id work). The cache is wiped on auto-lock or manual clear.

    Auto-lock

    After 5 minutes of inactivity a 60-second warning appears. If not dismissed, all key fields and cached keys are cleared from memory.
