# Changelog

All notable changes to the vault, newest first.

## 1.1.11 — 2026-07-03

A bug-fix release: the extension passkey fix below, plus one PWA-only cosmetic fix. No record-format, crypto, or wire-protocol change; `javascript.js` / `argon2-worker.js` are untouched (the PWA fix is pure CSS in `part1`, regenerated into `index.html`), so the extensions' code-integrity pins (`code-pins.js`) are unchanged. Verified: both extension self-tests (`node selftest.js`) pass, and the PWA fix is confirmed end-to-end in headless Chromium (long-named passkey entry: name ellipsizes, 🔐 stays fully visible, button does not overflow).

- **PWA — trailing modifier glyphs no longer truncate on long entry names**: the passkey (🔐) and secure-note (📝) badges were `.entry-lbl::after` pseudo-elements *inside* the entry-button label, which is `overflow:hidden; text-overflow:ellipsis`. On a name too long to fit, the ellipsis clipped the trailing glyph along with the overflowing text, hiding the fact that the entry held a passkey/note. The badges now render as `.entry-btn::after` — their own flex item on the button, a sibling of the (still-truncating) label — with the label changed from `flex:1` to `flex:0 1 auto` so it shrinks to its content and the glyph hugs the name. A flex item can't be clipped by the label's own `overflow`, so the glyph is always shown. Leading badges (favorite ★ on `.entry-btn::before`, stale ⏳ on `.entry-lbl::before`) were never affected — the ellipsis only truncates the tail — and all four can coexist on one entry. In multi-select mode the ✓ marker still wins the `::after` slot on a selected entry (unchanged precedence).
- **Extensions — passkeys can now be created on devices with no native platform authenticator (e.g. a Linux desktop)**: relying parties such as Google gate their *create-a-passkey* UI on `PublicKeyCredential.isUserVerifyingPlatformAuthenticatorAvailable()` (and, on Chrome 133+, `getClientCapabilities()`) **before** ever calling `navigator.credentials.create()`. The MAIN-world injector (Chrome `content_passkey_main.js`, Firefox `passkey-inpage.js`) previously overrode only `create`/`get`, so those probes reached the browser's native implementation and returned `false` where the OS has no built-in authenticator — the RP then showed "A passkey can't be created on this device" and the vault approval window never opened. Both injectors now also report the vault (a virtual platform authenticator that performs user verification via the master-password prompt) as available: `isUVPAA()` → `true`, and `getClientCapabilities()` merges `userVerifyingPlatformAuthenticator` / `passkeyPlatformAuthenticator: true` over the native result — only where the method already exists natively, never invented on browsers that lack it. The probe is passive, so this only affects sites that already offer passkeys; if the user declines the vault, `create()` still falls back to the browser's native authenticator as before. Applied byte-for-byte to both the Firefox and Chrome/Edge builds. (Cosmetic, unaffected: a `none`-attestation software authenticator emits an all-zero AAGUID, so browsers show a generic/guessed provider name for the stored passkey.)
- **Version sync**: PWA app, Firefox extension, Chrome extension, the terminal client (TUI), and the standalone Node server (`server.js`) all bumped to **1.1.11**.

## 1.1.10 — 2026-07-01

A security-audit remediation pass. No record-format or crypto change; one legacy write-protocol parameter is removed (below). Verified: the full `run-tests.sh` suite plus the PHP↔Node parity cases (including two new ones) pass.

- **Serving-layer deny rules for key material and operator files**: all three serving layers now refuse `*.pem` / `*.crx` / `*.xpi` / `*.sh` and **all dotfiles/dot-directories** (not just `.ht*`) — the root `.htaccess` (new `FilesMatch` + `RedirectMatch` rules), `server.js` (`DENY_EXT`), and the canonical nginx block in `README.md` (which live deployments must mirror). Trigger: the Chrome extension's **`.pem` signing key** — the trust anchor behind the extensions' code-integrity pinning — sat in the served webroot with no deny rule on any backend; it and the `.crx` have also been moved out of the web tree entirely. The service worker additionally refuses to cache those extensions (`SENSITIVE_EXT`). `regen.sh` now reads the Basic-Auth pair from `VAULT_AUTH_USER`/`VAULT_AUTH_PASS` instead of embedding it.
- **Apache: `moved/` is now denied** (`moved/.htaccess`, same shape as `bak/.htaccess`): the legacy working directory holds full ciphertext DB copies (`lines.params-new`, now chmod 600) and migration tooling; nginx and `server.js` already denied it, Apache did not.
- **Old-key ciphertext cleanup after a password/KDF change**: the whole-vault re-encrypt (`_reencryptVault`) now empties the `trash` after committing — its records are still encrypted under the *pre-change* passwords/cost (exactly the material a password change is meant to retire, and restoring one would re-add a record the current keys can't decrypt). The success toast tells the operator that server-side `bak/` retains pre-change snapshots for up to `VAULT_BAK_MAX_AGE_DAYS` (60 by default). Documented in `THREAT_MODEL.md`.
- **Write protocol: the legacy `delete=<index>` parameter is removed** (both backends now 400 it). No shipped client ever sent it, it had no staleness guard, and PHP's `intval()` semantics turned any malformed value into "delete record 0" — a data-loss footgun. Delete/edit have referenced records by content (`delete_rec`) since that path shipped. The `phpIntval` parity shim is gone with it; `parity-test.js` now asserts both backends reject the param identically.
- **`post.php`: origin check is port-aware**: the CSRF same-origin compare used `parse_url(..., PHP_URL_HOST)` (never carries a port) against `HTTP_HOST` (carries one on non-default ports), so every write on e.g. an `:8080` deployment was refused 403. It now compares `host[:port]`, matching `server.js`'s `URL.host` semantics; a new parity case drives post.php with a ported Host/Origin.
- **Extensions: passkey approval window's write-username prefill is sticky** (`storage.local.writeUser`, saved on each successful create) instead of hardcoding `pass` in both `background.js` files.
- **Deadwood**: removed `moved/search-bak.js` (stale copy of the search code) and `PASSKEY_PLAN.md` (the shipped feature's as-built docs live in `docs/passkeys.md`); `docs/deployment.md`'s summarized nginx deny list regained the `kdfparams` entry it had drifted from `README.md` on.
- **Version sync**: PWA app, Firefox extension, Chrome extension, the terminal client (TUI), and the standalone Node server (`server.js`) all bumped to **1.1.10**.

## 1.1.8 — 2026-06-30

A security-hardening pass closing the two highest-leverage gaps in the threat model: the served-code trust hole and a KDF-cost downgrade. No record format change; the on-disk **manifest** format gains a backward-compatible `vm2` variant (legacy `vm1` still verifies). Verified: the full `run-tests.sh` suite (client crypto/logic, server protocol + HTTP layer, both extension self-tests, the Playwright browser E2E, and 14/14 PHP↔Node parity) all pass.

- **Integrity manifest binds the KDF cost (`vm2`)**: the keyed integrity manifest now signs the active Argon2id cost (`a2id|m|t|p`) alongside the record set — `vm2|salt1|salt2|rev|ts|kdf|hmac`. Because the kdf string carries its own `|`, a vm2 manifest is 10 pipe fields (kdf at indices 5–8); `_parseManifest`, `is_valid_manifest()` (PHP), `isValidManifest()` (`server.js`), and both extensions' `parseManifest` agree. Verification derives at the manifest's **declared** cost (decoupled from the server-controlled embedded `#vault-kdf`) and compares declared-vs-served, so a server that swaps `kdfparams` to a weaker cost is caught — at verify, and at load via a password-free `_checkKdfBinding` (which catches it even when the wrong cost makes records fail to decrypt). Every write re-signs as vm2; legacy `vm1` manifests still verify and upgrade to vm2 on the next write.
- **Code-integrity pinning in the browser extensions** (closes the "compromised server can swap `javascript.js`" hole, out-of-band): on unlock each extension fetches the served `javascript.js` + `argon2-worker.js`, SHA-256s them, and compares against the hash pinned in the new `code-pins.js` (regenerated per release by `update-code-pins.sh`). On a mismatch the popup shows a prominent red banner and **disables autofill** (warn-not-block — unlock still works so the vault can be read/repaired); `unknown` (no pins, e.g. a dev build) and `error` (offline/404) never block. It fetches assets directly from the origin rather than trusting the service worker's `GET_ASSET_HASHES` hook (which a compromised server could also rewrite).
- **Version sync**: PWA app, Firefox extension, Chrome extension, the terminal client (TUI), and the standalone Node server (`server.js`) all bumped to **1.1.8**.

## 1.1.7 — 2026-06-30

A code-audit polish pass — no record-format, crypto, or wire-protocol change, and full byte-parity between `post.php` and `server.js` is preserved (now proven by 13/13 parity cases). Verified: the full `run-tests.sh` suite (client crypto/logic, server protocol + HTTP layer, both extension self-tests, the Playwright browser E2E, and PHP↔Node parity) all pass.

- **`server.js` — writes require POST in every mode**: a bare `GET /post.php` in **local** mode previously fell through to the write path and triggered a no-op rewrite of `lines`/`index.html` plus a fresh `bak/` backup (a typed URL or a browser prefetch could churn backups). Local mode has no auth/CSRF by design, but a write must still be a POST — `post.php` already `403`s every non-POST, non-`regen` request, so this restores parity and keeps `GET` side-effect-free. (`regen` via `GET` is still allowed.)
- **`server.js` ↔ `post.php` — `delete` index parity**: a malformed `delete` value (e.g. a non-numeric string) was parsed differently by the two backends — PHP's `intval('abc')` is `0` (deletes record 0) while JS's `parseInt('abc')` is `NaN` (deleted nothing), so the same crafted request could produce divergent `lines` and a divergent signed manifest. A new `phpIntval()` helper makes `server.js` match PHP's `intval` semantics exactly. The trusted client never sends this, but it closes a cross-backend divergence; a new `parity-test.js` case (`delete with non-numeric index`) guards it.
- **`server.js` — backup-filename timestamp fix**: the sub-second suffix on `bak/lines.*` was derived from `process.hrtime` (a *monotonic* clock unrelated to wall time), so within a single second the suffix did **not** order chronologically — breaking the "lexical sort = oldest first" assumption the backup pruner relies on. It is now derived from the same wall-clock instant as the rest of the filename (mirroring `post.php`'s `microtime` fractional part).
- **Cache policy consistency (`.htaccess`)**: the `Cache-Control: no-store` header is now scoped to `index.html` only (matching `server.js`), instead of being applied to every file. The non-secret code assets (`javascript.js` ~360 KB, `argon2-worker.js`) may now cache under Apache instead of being re-downloaded on every load; `index.html` (which embeds the ciphertext DB) still stays `no-store`.
- **Internal cleanups (no behavior change)**: the three near-identical vault-lock paths (`clearLines`, `_lockAndClearVault`, `performAutoLock`) now share one `_lockCore()` helper, so the security-sensitive teardown (wipe master keys, tear down the Argon2id worker pool, clear the clipboard, re-lock the grid) can't drift between them; the two duplicated clipboard-copy paths (`doCBCopy`, `_copyValue`) share one `_armClipboard()` so the dirty-flag + auto-clear contract is defined once; a redundant boolean expression and an unused parameter were removed from `server.js`; and `docs/versioning.md` now states the correct current version.
- **Version sync**: PWA app, Firefox extension, Chrome extension, the terminal client (TUI), and the standalone Node server (`server.js`) all bumped to **1.1.7**.
